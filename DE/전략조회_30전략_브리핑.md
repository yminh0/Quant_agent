# 전략 조회 성능 브리핑: 30전략 종합판

작성일: 2026-08-11

## 0. 한 줄 결론

- 원본 `db.py`는 전략 1개가 들어와도 **보조 가격 이력(path)**, 전일 RSI, 재무 SQL을 넓게 읽는다.
- 현재 개선판은 `ai/ai_graph/data_sources/profile_aware.py`가 사실상 `db_test.py` fast-path를 노출하며, **전략 분류 결과에 따라 필요 없는 조회를 건너뛴다**.
- 이번 30전략 종합판에서는 **기술형 25개에서 큰 개선**, **재무형 5개에서는 개선폭이 작음**이 같이 확인됐다.
- 즉, 이번 최적화의 핵심은 “DB가 계산을 못 해서 느린 것”이 아니라, **전략 1개에 대해 읽는 범위를 줄인 것**이다.

## 1. 처음 보는 사람용 요약

| 용어 | 뜻 |
|---|---|
| `db.py` | 원본 로더. 전략 입력이 오면 여러 큰 테이블/뷰를 넓게 읽는다. |
| `db_test.py` | 개선판 구현. `profile_aware` 계열 fast-path를 담는다. |
| `profile_aware.py` | 현재 보고서/배포에서 쓰는 이름. 내부 구현은 `db_test.py`를 따른다. |
| `path` | 최근 20일/60일/252일 같은 **보조 가격 이력**. RSI/20일선/돌파 판단에 쓰인다. |
| `load()` 시간 | 전략 입력 후 `load_pipeline_data_from_env()`가 DB에서 데이터를 읽는 데 걸린 시간. |

## 2. 문제 상황

원본 구조에서는 전략 문장이 들어와도 다음을 거의 항상 같이 읽었다.

1. 현재 후보 프레임(`mart.kis_adjusted_feature_frame_asof`)
2. 보조 가격 이력(path)
3. 전일 RSI
4. DART 재무 조회
5. 백테스트용 가격 행과 추가 타임라인

문제는 이 중 일부가 **모든 전략에 꼭 필요한 건 아니었다**는 점이다. 예를 들어 RSI/20일선/볼린저 같은 기술형 전략은 보조 이력을 크게 줄여도 된다. 반면 저PER·ROE 같은 재무형 전략은 DART 조회가 여전히 필요하다.

## 3. 개선 가설과 작업 내용

### 개선 가설

- 전략을 먼저 **프로파일(profile)** 로 분류하면,
- 그 프로파일이 정말 쓰는 데이터만 읽을 수 있고,
- 그러면 DB 조회 시간이 줄어든다.

### 작업 내용

| 파일 | 역할 |
|---|---|
| `ai/ai_graph/data_sources/db.py` | 원본 baseline. 현재 실험 비교 기준. |
| `ai/ai_graph/data_sources/db_test.py` | fast-path 구현. 기술형 전략은 path 조회를 줄이고, 필요할 때만 DART를 붙인다. |
| `ai/ai_graph/data_sources/profile_aware.py` | 현재 배포/보고서용 이름. 내부적으로 `db_test.py`를 노출한다. |

핵심 아이디어는 다음과 같다.

- `rsi_rebound`, `pullback_trend`, `bollinger_squeeze` 같은 기술형은 path를 줄이거나 건너뛴다.
- `value_quality`, `quality_growth`, `growth_momentum` 같은 재무형은 DART를 읽지만, 불필요한 path는 줄인다.
- 후보 정렬은 실제 path 계산 대신 **proxy ranking** 으로 유지해, 기존 후보 cap 로직이 계속 동작하도록 했다.

> 이번 실험은 materialized view를 새로 만든 것이 아니라, **조회 경로 자체를 덜 읽게 바꾼 것**이다.

## 4. 실험 방법

| 항목 | 내용 |
|---|---|
| 기준 코드 | `ai/ai_graph/data_sources/db.py` |
| 개선 코드 | `ai/ai_graph/data_sources/profile_aware.py` → `ai/ai_graph/data_sources/db_test.py` |
| 측정 대상 | `load_pipeline_data_from_env()` 실행 시간(`data_load_seconds`) |
| 측정 범위 | 전략 입력 후 DB에서 데이터를 읽어오는 구간 전체 |
| 25개 기술형 전략 | 기존 검증된 벤치마크 코퍼스 재사용 |
| 5개 재무형 전략 | 오늘 추가 실측 |

### 왜 30개인가

- 25개는 기존에 DART를 쓰지 않는 기술형 전략들이다.
- 5개는 DART가 실제로 필요한 재무형 전략을 추가해, fast-path가 어디까지 먹히는지 확인하기 위해 넣었다.
- 따라서 이 30개는 “기술형에서의 큰 개선”과 “재무형에서의 제한된 개선”을 함께 보여준다.

- 전체 30개 평균은 `141.36s → 71.14s` 수준으로 줄었고, 평균적으로 **49.68% 개선**이었다.

## 8. 결론 / 트레이드오프

### 결론

- 이번 개선의 본질은 **“전략 1개를 위해 읽는 범위를 줄인 것”**이다.
- 기술형 전략에서는 `profile_aware` fast-path가 매우 잘 먹혔다.
- 재무형 전략은 DART 자체가 필요해서, 개선폭이 작거나 거의 없었다.
- 따라서 이 최적화는 **모든 전략을 똑같이 빠르게 만드는 해결책이 아니라**, “잘 맞는 전략을 크게 빠르게 만드는 해결책”이다.

### 트레이드오프

- 프로파일 분류가 틀리면 잘못된 데이터 조합이 나올 수 있다.
- DART 기반 전략은 여전히 무겁다. 나중에는 `mart.dart_financial_asof` materialization 같은 구조적 개선이 별도로 필요할 수 있다.
- 반대로 기술형은 지금 방식만으로도 체감 성능 개선이 충분히 크다.

## 9. 브리핑용 한 줄 요약

> “원본은 전략 1개마다 큰 보조 데이터(path·DART)를 넓게 읽었고, 개선판은 전략 프로파일을 먼저 판별해서 필요 없는 조회를 건너뛰도록 바꿨다. 기술형 25개는 크게 빨라졌고, 재무형 5개는 DART 때문에 개선폭이 작지만 전체 평균은 절반 수준으로 줄었다.”
