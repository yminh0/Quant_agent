# AI 파이프라인 Data Node 점검 및 개선안

## 한줄 요약

Data Node는 전략 요청을 데이터 조회 계획으로 바꾸고, 스크리닝·백테스트·데이터 품질 정보를 다음 단계에 전달한다. 현재는 소스별 계약 차이, 큰 조회량, 조건 자동 완화, 부분 실패 허용이 주요 문제다.

## 현재 문제점

| 문제 | 영향 |
| --- | --- |
| `db`, `db_test`, `db_split`, `profile_aware`의 입력·출력 계약이 다름 | 환경에 따라 실행 오류가 나거나 결과가 달라질 수 있음 |
| DSN이 없을 때 fixture로 실행 가능 | 운영 설정 오류가 실제 분석처럼 보일 수 있음 |
| 가격·지표·재무·스크리닝을 한 요청에서 모두 조회 | 응답 시간이 길고 메모리 사용량이 큼 |
| 후보가 없으면 조건을 자동 완화 | 원래 요청을 만족하지 않는 종목이 결과에 포함될 수 있음 |
| 일부 지표 조회 실패 후에도 계속 진행 | 조건을 평가하지 못한 전략이 정상 백테스트처럼 보일 수 있음 |
| 현재 후보와 과거 백테스트 유니버스를 함께 반환 | 추천 종목으로 과거 성과를 검증했다는 오해가 생길 수 있음 |
| Data Node 안에 조회, 품질 검증, 후보 생성, 상태 결정이 모두 있음 | 수정 범위가 커지고 장애 원인 파악이 어려움 |

## 수정 우선순위

### P0. 실행 계약과 운영 경계 정리

- 모든 데이터 소스가 같은 `load()` 인자와 `PipelineDataBundle`을 사용하게 한다.
- 운영에서는 `db`만 허용하고 나머지는 테스트·성능 측정에서만 사용한다.
- 운영에서 DSN이 없거나 출처가 PostgreSQL이 아니면 즉시 중단한다.
- fixture는 개발·계약 테스트 전용으로 제한한다.
- 전략에 필요한 지표가 없으면 사용 가능한 조건만으로 진행하지 않는다.

### P1. 결과 정합성 확보

- 스크리닝은 원래 조건을 그대로 적용하는 것을 기본값으로 한다.
- 조건 완화가 필요하면 사용자 동의를 받고, 엄격한 후보와 완화 후보를 분리한다.
- 완화 후보는 자동 추천과 백테스트에 사용하지 않는다.
- `current_screen_candidates`와 `historical_backtest_universe`를 별도 필드로 관리한다.
- Data Node 안의 LLM 호출은 Research 또는 전략 해석 단계로 옮긴다.

### P1. 조회량과 메모리 줄이기

- 확정된 전략 명세에서 필요한 지표와 기간만 조회한다.
- 사용하지 않는 재무·기술 지표는 읽지 않는다.
- 대용량 가격 데이터를 상태에 통째로 복사하지 말고 snapshot ID, 캐시, cursor 방식으로 전달한다.
- 현재 스크리닝과 과거 백테스트 데이터 조회 시간을 따로 기록한다.
- 실제 조회 기간이 짧아지면 결과에 "검증 기간 부족"을 표시한다.

### P2. 내부 책임 분리

Data Node를 다음 네 단계로 나누면 관리하기 쉽다.

1. 조회 계획 작성
2. 데이터 존재·기준일 확인
3. 필요한 데이터 조회
4. 품질 검증 후 다음 노드에 전달

처음부터 그래프 노드를 추가하기보다 내부 함수와 반환 계약부터 분리하는 편이 안전하다.

## 완료 기준

- 운영 분석은 PostgreSQL 데이터로만 실행된다.
- 데이터 소스 변형에 따라 같은 요청의 결과가 달라지지 않는다.
- 필수 데이터가 없으면 백테스트 대신 명확한 데이터 부족 상태로 끝난다.
- 엄격한 후보, 완화 후보, 현재 후보, 과거 유니버스가 서로 섞이지 않는다.
- 기준일, 신선도, 조회 기간, 실패 원인이 로그와 결과에 남는다.
