## 문제

`AI_ANALYSIS_MAX_CONCURRENCY`의 코드 기본값은 `4`다
(`ai/ai_graph/analysis_capacity.py:37`). README가 적어둔 근거는 **프로바이더 축
하나뿐**이다.

> `AI_ANALYSIS_MAX_CONCURRENCY` | `4` | 동시에 실행할 분석 수.
> AOAI 게이트 capacity(8)보다 낮게 둔다 — 분석 1건이 프로바이더 호출을 여러 번 내므로

CPU 축은 이 근거에 들어 있지 않다. 그런데 분석 1건은 프로바이더만 쓰는 게 아니라
후보를 프로세스 풀로 펼친다.

## 관측한 사실

### 1. 프로바이더 축 근거의 `8`은 운용값이 아니라 천장이다

`ai/ai_graph/llm/concurrency_gate.py`:

| 상수 | 값 | 의미 |
|---|---|---|
| `DEFAULT_INITIAL_CAPACITY` | **2** | 게이트가 시작하는 용량 |
| `DEFAULT_MIN_CAPACITY` | 1 | 하한 |
| `DEFAULT_MAX_CAPACITY` | **8** | 성장 상한 |
| `DEFAULT_HEALTHY_OBSERVATIONS_TO_GROW` | 10 | 한 단계 올리는 데 필요한 연속 정상 응답 수 |

게이트는 `2`에서 시작해 정상 응답 10회마다 한 단계씩만 올라간다. 즉 평상시 운용
용량은 `8`이 아니라 `2` 근처이고, README가 인용한 `8`은 **한참 뒤에야 도달하는
천장**이다. 동시 분석 `4`는 그 천장보다 낮지만 **시작 용량보다는 높다.**

### 2. 프로세스 풀 워커 합계에는 전역 상한이 없다

`ai/ai_graph/nodes/backtest.py:1273` `_candidate_worker_count`:

```python
requested = max(1, min(candidate_count, requested, available_cpus))
```

`available_cpus = os.cpu_count()`가 **분석 1건의** 풀 크기를 묶는다. 분석 여러
건에 걸친 워커 **합계**를 묶는 것은 없다. `AI_BACKTEST_WORKERS`의 기본값은 `2`
(`backtest.py:132`)이므로, 코어가 2개인 호스트에서:

```
동시 분석 4건 × min(candidate_count, 2, 2) 워커 = 최대 8개 CPU 바운드 프로세스
```

코어 2개 위에서 8개다. 상한이 아니라 **4배 과구독**이다.
(단, `candidate_count * row_count < 250_000`이면 `_candidate_worker_count`가 `1`을
돌려주므로 작은 분석은 직렬로 돈다. 과구독은 큰 분석이 겹칠 때 나타난다.)

`AnalysisCapacityGate`가 존재하는 이유가 모듈 docstring에 적혀 있다 — "어느 지점을
넘으면 프로세스는 느려지는 게 아니라 죽는다." 그 지점을 프로바이더 축으로만 정했다.

서버 셸에 접근할 수 없어서 앞의 셋을 읽지 못했다. 로컬에 배포 키가 없고

있다. 이 값들은 **내가 다시 관측한 것이 아니다.** 아래 판단은 그 수치가 맞다는
가정 위에 서 있고, 가정이 틀리면 결론도 바뀐다.

## 결정 요청

### 선택지

**A. 현행 유지 + 근거만 보강**
값을 바꾸지 않고 README에 CPU 축 근거와 실측 미확인 사실만 적는다.

**B. 기본값을 코어 수에 연동한다**
`DEFAULT_MAX_CONCURRENCY`를 상수 `4` 대신 `min(4, os.cpu_count() or 1)`로 둔다.
2코어 호스트에서 자동으로 2가 되고, 큰 호스트에서는 지금과 같다.

**C. 프로세스 풀에 전역 워커 예산을 둔다**
분석 간 워커 **합계**에 상한을 둬서, 동시 분석 수와 무관하게 CPU 바운드 프로세스가
코어 수를 넘지 않게 한다.

### 권고안

**B를 먼저, C는 별도 행으로 분리.**

### 권고 근거

- B는 되돌리기 쉽고 관측 없이도 안전한 방향이다. 코어보다 많은 분석을 동시에 띄우지
  않는다는 성질은 어떤 호스트에서도 참이며, 큰 호스트에서는 현행과 동일하다.
- A는 관측된 과구독(2코어 × 8프로세스)을 문서로만 남기고 방치한다. 문제를 아는 채로
  두는 선택이다.
- C가 근본이다. B는 동시 분석 수만 줄일 뿐, "분석 1건이 코어 수만큼 펼칠 수 있다"는
  성질은 그대로다. 다만 C는 프로세스 풀 수명주기를 건드리므로 이 결정과 같은 크기가
  아니다. 별도 행으로 다뤄야 한다.
- 상한을 넘은 잡은 거절이 아니라 대기(`QUEUED`)이므로, B가 낮추는 것은 처리량이지
  성공률이 아니다. 대기 한도는 `AI_ANALYSIS_QUEUE_WAIT_SECONDS=600`으로 이미 넉넉하다.

### 확신수준

**0.45**

### 확신수준 근거

결정에 필요한 입력 6개 중 **4개를 관측했고 2개를 관측하지 못했다**(서버 `nproc`,
서버 env 실제 값). 미관측 2개가 결론을 뒤집을 수 있는 지점:

- 서버 코어가 2개가 아니라 4개 이상이면 과구독 폭이 줄고 B의 이득이 사라진다.
- 서버 `.env`가 이미 낮은 값을 설정하고 있다면 이 검토는 코드 기본값에만 해당하고
  운영에는 영향이 없다.

**서버 `nproc`과 두 env 값을 읽는 것이 이 결정의 선행 작업이다.** 서버 셸 접근이
있는 사람이 그 셋을 기록해 주면 확신수준을 올릴 수 있다.

## 함께 확인한 문서 결함

  시작 용량은 `2`다.
- `AI_BACKTEST_WORKERS`(기본 `2`)는 README 환경변수 표에 없다. 분석 1건의 CPU 사용량을
  직접 정하는 값인데 문서화되어 있지 않다.
