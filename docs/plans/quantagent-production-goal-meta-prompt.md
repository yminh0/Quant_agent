# QuantAgent 신뢰성 재수립 메타 프롬프트

## 이 프롬프트의 용도

이 문서는 QuantAgent의 다음 계획·개발 사이클을 시작할 때 리더 에이전트에게 그대로 전달한다. 목표는 작업을 많이 끝낸 것처럼 보이게 하는 것이 아니다. 사용자가 분석 결과를 보고 "이 숫자가 무엇을 뜻하고, 언제 믿지 말아야 하는지" 스스로 판단할 수 있는 상태를 만드는 것이다.

## Goal

실시간 온디맨드 전략 추천을 제품·API·작업 큐·화면에서 제거하거나 명시적으로 비활성화한다. 대신 실제 데이터와 명시적 개발 fixture를 구분하고, 각 퀀트 지표의 산출 근거·시점·한계·실패 사유를 사용자 화면에서 확인할 수 있으며, 인증과 오류 상황에서도 사용자가 다음 행동을 알 수 있는 검증 제품 기준선을 만든다.

이 Goal은 다음 조건을 모두 만족할 때만 완료다.

1. 온디맨드 분석·추천의 공개 진입점, API, 작업 생성 경로, 큐 소비자, CTA, 문구를 인벤토리로 남긴다. 신규 요청을 만들 수 있는 공개 경로는 0개여야 하며, 남겨야 하는 과거 결과는 읽기 전용 보관 상태·비활성 사유·대체 다음 행동을 표시한다.
2. 운영 경로에서 AOAI, DB, provider, 스키마 오류가 fixture, mock, 0점, 과거 캐시를 정상 분석 결과처럼 바꾸지 않는다.
3. 공개되는 모든 지표는 정의, 수식 또는 산출 절차, 단위, 분모, 기간, as-of, 입력 데이터 버전 또는 해시, 실행 ID, freshness, 결측·0·비유한값 정책을 가진다. 하나라도 없으면 "검증 불가"로 표시한다.
4. 백테스트 결과는 point-in-time 유니버스, 상장폐지 처리, 워밍업, 체결·비용 가정, 후보 수, OOS 경계를 증적 없이 추천·우수·검증 완료로 표현하지 않는다.
5. 로그인 실패, 세션 만료, rate limit, 데이터 부족, provider 실패, 결과 없음, stale 데이터가 사용자에게 기술 용어·내부 코드 없이 원인 범주와 안전한 다음 행동을 보여 준다.
6. P0 작업은 코드 변경, 자동 테스트 명령, 실제 결과, 증적 URI, 승인자 없이 Done이 될 수 없다.
7. 진행률은 사람의 임의 퍼센트가 아니라 증적이 충족된 원자 작업의 집계다. 배포 가능 상태와 진척률은 별도로 보여 준다.

## 금지선과 비목표

- 새 온디맨드 추천 기능, 새 전략군, 수익률을 높인다는 표현, UI 장식은 위 계약을 통과하기 전에는 시작하지 않는다.
- 인증을 우회하거나 실제 사용자 세션·비밀값·외부 계정을 사용하지 않는다.
- fixture를 없애지 않는다. 개발 전용 모드로 분리하고 화면·로그·지표에서 실제 데이터와 혼동되지 않게 한다.
- 백테스트 성과가 미래 수익을 증명한다는 문구를 쓰지 않는다.
- 완료되지 않은 리서치, 미실행 통합 테스트, 인증이 필요한 화면을 PASS로 기록하지 않는다.

## 시작 전 리더의 의무

1. `banker-deep-research`로 아래 다섯 각도를 독립 조사한다. 각 주장마다 출처, 반증, 재현성 한계, confidence를 적는다.
   - 백테스트 편향과 OOS 검증
   - 지표 정의·데이터 계보·freshness
   - LLM·provider 오류와 fail-closed 계약
   - 금융·인증 UX의 이해도와 복구 경로
   - 증적 기반 일정·진행률 관리
2. 저장소에서 실제 구현과 테스트를 읽고, 주장마다 `file:line` 또는 실행 출력으로 교차 확인한다. 기존 문서는 출발점일 뿐 사실의 대체물이 아니다.
3. `banker-ultra-ui-qa`로 라이브 페이지를 브라우저에서 확인한다. 인증이 필요한 화면은 세션 seed가 없으면 "미검증"으로 남긴다. 로그인 월을 PASS로 오인하지 않는다.
4. 아래 Goal bootstrap 계약을 채운다. evaluator 명령과 PASS/FAIL 계약이 생기기 전에는 `performance-goal`을 시작하지 않는다.

## Goal bootstrap 계약

Goal은 대화 속 다짐이 아니라 재현 가능한 상태 기계다. 아래 블록을 비워 둔 채 Goal이나 Team을 시작하면 안 된다.

```text
Goal ID: QAG-PROD-TRUST-001
Objective: 온디맨드 분석·추천을 제거/비활성화하고, 검증 불가한 데이터·지표·오류를 성공 결과로 표시하지 않는 출시 기준선을 만든다.
Scope: docs/plans의 계획 산출물, 이후 WBS가 지정하는 단일-커밋 구현 작업
Out of scope: 실거래 주문, 계정·비밀값 열람, 신규 추천 기능, 수익률 목표
Evaluator: <WBS-GATE-001의 고정 명령; 아직 미정이면 START 금지>
PASS: 모든 P0 행에 code diff + command exit 0 + output URI + 승인자, 공개 UX matrix PASS, 독립 QA APPROVE
FAIL: P0 하나라도 누락·미검증·fixture 성공 위장·공개 dev 노출·formula 불일치
STOP: 외부 권한/인증 세션/사람 결정이 필요하면 해당 Goal을 blocked로 기록하고 범위를 넓히지 않는다.
```

1. `docs/plans/quantagent-production-goal-state.md`에 위 블록, evaluator 버전·명령, 생성 시각, owner, 상태(`draft → created → running → checkpointed → complete|blocked`)를 기록한다.
2. evaluator가 WBS-GATE-001로 고정되고 사전 실행에 성공한 뒤에만 `omx performance-goal create`와 `omx performance-goal start`를 실행한다. CLI 출력과 Goal 상태 파일 경로를 control board 증적으로 남긴다.
3. Team 시작 프롬프트에는 Goal ID, objective, 금지선, 현재 상태, 각 작업의 ID·입력·출력·의존성·완료 증적, 충돌 해결 규칙을 그대로 넣는다. 각 작업자는 Goal 완료를 선언할 수 없고, 일정·증적 매니저만 checkpoint를 갱신한다.
4. checkpoint는 적어도 blocker 발견·해제, P0 작업 완료, 독립 QA 결과마다 갱신한다. `complete`는 evaluator PASS와 독립 QA APPROVE가 같은 revision을 가리킬 때만 가능하다.

## 팀 구성과 관할

작업자는 역할이 아니라 산출물 경계로 나눈다. 같은 파일이나 같은 수용 기준을 두 명이 동시에 소유하지 않는다.

| 관할 | 산출물 | 다른 관할과의 인터페이스 |
|---|---|---|
| 제품 신뢰 리드 | Goal, 금지선, 출시 게이트 | 다른 모든 작업의 우선순위·차단 해제 승인 |
| 퀀트 검증 리드 | bias, OOS, warm-up, 체결·비용·유니버스 계약 | 지표 사전과 UI 노출 필드 요구 |
| 데이터·AI 신뢰 리드 | provider 오류 taxonomy, mock 격리, 계보 API | UI가 표시할 상태와 증적 필드 제공 |
| UX 검증 리드 | 인증, empty/error/stale, 정보 계층, Playwright 증적 | API 계약을 사용자 문구·행동으로 변환 |
| 용어 검사자 | 사용자 용어, 수식 명칭, 기술 용어 경계 | 지표 사전과 화면 카피의 불일치 blocker |
| 맥락·근거 검토자 | 기존 대화, 문제 정의, 실험 리포트, 결정 이력의 요구사항 추적표 | 빠진 맥락과 상충 결론을 WBS 동결 blocker로 등록 |
| 성숙도 비교 리드 | 유사 제품·오픈소스 대비 production maturity 기준선과 개선 우선순위 | 비교 대상·버전·평가축·점수식·재현 명령을 고정 |
| 일정·증적 매니저 | WBS, 의존성, 용량, risk, control board | task 상태 집계. 구현 범위는 소유하지 않음 |
| 독립 심사자 | 수용 기준 누락, 반증, 회귀 위험 | 저자 요약이 아닌 원 요청·git diff·기준 파일로 심사 |

## 원자 작업 계약

모든 WBS 행은 하나의 **의도된 커밋**으로 끝날 수 있어야 한다. 한 커밋에 여러 WBS 행을 넣거나, 한 WBS 행을 여러 커밋에 나누지 않는다. 커밋 제목은 저장소의 `[TYPE] 제목` 관례를 따른다. 한 행에는 아래 필드를 빠짐없이 둔다.

`ID | Epic | 작업 | 의도된 커밋 제목 | 소유자 | 백업 | 역량 적합도 | 최대 WIP | 선행 조건 | 추정 | 위험 | 변경 경로 | 자동 검증 명령 | 사람 검토 | 증적 URI | 승인자 | 상태`

- 작업은 동사로 시작하고, "개선", "고도화", "정리"처럼 결과를 판정할 수 없는 말은 쓰지 않는다.
- P0는 실제 실행 출력이 없는 한 `Done`이 아니다.
- `Blocked`, `검증 실패`, `승인 대기`, `증적 누락`은 0%와 다르다. control board에서 별도로 센다.
- 일정·증적 매니저는 개인별 가용 시간, 역량 적합도, 최대 WIP, 주·백업, SPOF를 capacity matrix로 유지한다. 한도 초과·핵심 경로 단독 소유·백업 부재는 WBS 동결 blocker다.
- 같은 원인이 세 번 재발하면 새 작업을 추가해 덮지 않는다. 원인 분석과 사람 결정 항목으로 올린다.
- 가용 시간·기간·실명 배정이 제공되지 않으면 값을 추정하지 않는다. 해당 역할은 `사람 결정 필요`로 두고, 일정은 상대 작업일과 의존성까지만 확정한다.

## 성숙도 비교 게이트

WBS를 동결하기 전에 성숙도 비교 리드는 비교 기준선을 만든다. 비교의 목적은 유사 제품을 흉내 내는 것이 아니라, 사용자에게 미치는 위험과 운영 완성도를 정량화하는 것이다.

- 비교 대상은 최소 3개다. 각 대상의 제품 또는 오픈소스 버전, 조사 날짜, 공개 근거 URL, 라이선스·운영 범위를 기록한다.
- 평가축은 `실데이터·fixture 분리`, `실패 투명성`, `지표 정의·계보`, `백테스트 타당성`, `인증·복구 UX`, `배포 재현성`, `관측성·증적`이다.
- 축마다 0~4 점의 행동 기준, 근거 링크 또는 `file:line`, 재현 명령을 둔다. 총점만으로 출시를 판단하지 않는다. P0 축이 0 또는 1이면 배포 가능은 No다.
- 성숙도 비교는 매 릴리스 후보와 기준 변경 때 다시 실행한다. 비교 불가인 축은 0점이 아니라 `미평가`로 표시하고 출시 판단에서 제외하지 않는다.

## 협의 규칙

1. 의견이 충돌하면 더 그럴듯한 설명이 아니라 더 좁고 재현 가능한 수용 기준을 채택한다.
2. 정량 주장에는 데이터 기간, 샘플 수, 후보 수, seed, 실행 명령을 붙인다. 없는 숫자는 추정치로 표시한다.
3. UI 판단에는 `URL | viewport | 인증 상태 | seed 출처 | 시나리오 | 기대 문구 | 다음 행동 | DOM | network | console | screenshot | 접근성 결과`를 남긴다. 인증 세션이 없으면 해당 행은 명시적으로 `미검증`이며, 사람이 수행할 gate와 증적 슬롯을 남긴다.
4. 독립 심사자는 `banker-ralph-qa` 방식으로 설계·수용 기준·적대적 반증을 분리해서 평가한다. blocker를 낸 심사자가 재검증해 해제할 때까지 완료 처리하지 않는다.
5. 외부 모델 좌석이 없으면 모델 독립성이 미커버라는 사실을 기록한다. 외부 좌석이 없다는 이유로 내부 blocker를 완화하지 않는다.
6. 맥락·근거 검토자는 기존 문서의 주장마다 `원문 위치 | 현재 코드 근거 | 현재 테스트 결과 | 유지·수정·폐기`를 기록한다. 이 추적표가 없으면 WBS를 동결하지 않는다.
7. 리서치 주장은 `Claim ID | 주장 | 출처 URL·발행일 | 권위 등급 | 반증·한계 | confidence | 현재 HEAD 상태(active/fixed/regressed/unreproduced) | WBS 수용 기준 ID`를 가진 원장에만 "확인됨"으로 기록한다. 과거 문서와 검색 요약은 원장 이전에는 후보일 뿐이다.

## 실행 가능한 P0 수용 기준 템플릿

각 failure route는 별도 원자 작업으로 분해한다. `no DSN`, `DB 연결 실패`, `AOAI/provider timeout`, `인증 실패`, `schema mismatch`, `빈 응답`, `L4 증적 없음`, `persistent job store 없음`, `fixture/mock 명시 모드`, `stale 데이터`, `비유한 지표` 각각에 대해 API 상태, 화면 상태, 추천 차단, 증적 필드를 테스트한다.

예: `no DSN` 작업은 release profile에서 readiness 실패 또는 `분석 불가` 응답을 내고, `ready` 상태·양수 수익률·추천 카드·fixture freshness=0이 노출되지 않는 API와 브라우저 테스트가 모두 통과해야 한다.

모든 지표는 registry에 `표시명 | 사용자 용어 | 정의 | 공식 | formula_version | implementation path+hash | input window | unit/scale | denominator | as-of | source/dataset version | transform run ID | freshness | null/zero/non-finite policy | expected fixture/edge output`을 가진다. registry, JSON, 엔진, 카드가 행 단위로 일치하는 contract test가 P0 Done 조건이다.

## control board 갱신 규칙

계획 시작, 작업 시작, 테스트 종료, blocker 발견, 승인, 배포 판단 때마다 `docs/plans/quantagent-production-control-board.md`를 갱신한다. 상태 전이에는 이전 상태, 새 상태, revision, 시각, 증적 URI를 남긴다.

- 진행률 = 증적이 충족된 원자 작업 수 / 전체 원자 작업 수
- P0 완료율과 전체 완료율을 함께 표시한다.
- blocker에는 ID, 발견 시각, 근거, 영향 작업, 다음 확인 시각, 소유자, 재발 횟수, 마지막 심사자, 해제 증적을 남긴다.
- 증적 URI가 빈 작업은 완료율에 넣지 않는다.
- 배포 가능은 모든 P0 수용 기준과 독립 QA가 통과한 경우에만 `Yes`다.
