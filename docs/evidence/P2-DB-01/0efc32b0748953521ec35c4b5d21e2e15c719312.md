# P2-DB-01 owner execution 증적 묶음

> 이 문서는 **owner execution evidence**다. independent QA verdict 문서가 아니며,
> owner가 자신의 구현을 QA하거나 승인 판정을 내리지 않는다. 최종 검증과 승인은
> WBS-designated approver가 별도 문서로 수행한다.

## 1. 대상

- wbs_id: `P2-DB-01`
- 작업 원문: `backup restore의 RTO/RPO와 schema consistency를 기록한다.`
- Done · QA 계약: `RTO/RPO/consistency evidence`
- WBS 지정 실행·검증(literal verifier): `cd service_db && pytest -q`
- 의도된 커밋: `[DB] benchmark backup restore objective`
- owner implementation commit: `0efc32b0748953521ec35c4b5d21e2e15c719312`
- parent (baseline): `b9cdd5eda64c6b8804583f0e9eb930dc19b880d8`
- branch: `db/p2-db-01-recovery-benchmark`
- Workspace lock: `LOCK-DE-DB-01 · service_db/**, ai/tests/contract/**, ai/tests/release_evaluator/**`

WBS 기준은 온라인 스프레드시트이며, 이 문서는 로컬 최신 WBS export snapshot을 근거로
작성했다. 온라인 WBS의 실시간 최신 상태를 확인했다고 주장하지 않는다.

## 2. 기존 증적

WBS `증적 묶음 URI` 칸은 `실행 후 URI · exit=0 · reviewer 기록` placeholder 상태였고,
`상태·계약`은 `대기`였다. 이 ID를 다루는 기존 evidence 문서는 없었다.

선행 맥락: `P1-DB-01`(`fe9372f`, PR #10)이 migration rollback/forward replay drill과
catalog fingerprint 검증 인프라를 제공한다. 이 구현은 그 위에 얹은 확장이며 P1 산출물을
수정하지 않는다.

## 3. 구현 요약

실제 PostgreSQL logical backup/restore drill을 추가했다. 기존 migration restore
benchmark는 그대로 유지되며, 두 backend가 하나의 artifact 계약을 공유한다.

| backend | 메커니즘 | 데이터 복원 | `is_backup_restore_rto` |
|---|---|---|---|
| `migration_replay` | rollback SQL → forward migration | 없음 | `false` |
| `logical_backup` | actual `pg_dump` → actual `pg_restore` | 있음 | `true` |

추가 파일 (전부 신규, 3개):

- `service_db/scripts/benchmark_recovery_objective.py`
- `service_db/tests/test_recovery_objective_benchmark.py`
- `service_db/docs/recovery-objectives.md`

변경하지 않은 것:

- `service_db/scripts/verify_fixed_migration_replay.py`
- `service_db/scripts/run_fixed_migration_replay.py`
- `service_db/tests/test_migration_restore_drill.py`
- `service_db/tests/test_sql_migration.py`
- `service_db/tests/test_analysis_result_migration.py`
- `service_db/migrations/**` — 신규 migration 추가 0건, 기존 migration 수정 0건
- `service_db/rollbacks/**`

commit의 name-status는 3건 모두 `A`(added)이며 `M`/`D`/`R` 항목이 없다.

schema consistency는 P1의 `_catalog_union` / `_catalog_fingerprint`를 호출 재사용했고
중복 구현하지 않았다.

## 7. RTO evidence 상세

측정 범위:

- 시작: `pg_restore` 호출 직전
- 종료: `pg_restore` 완료 + post-restore catalog fingerprint 확인 + probe data 검증 완료

| run | `backup_creation_duration_seconds` | `logical_backup_restore_duration_seconds` | dump bytes |
|---|---|---|---|
| 1 | `0.643181` | `3.079792` | `154173` |
| 2 | `0.703919` | `3.233122` | `154173` |
| 3 | `0.699796` | `3.350510` | `154173` |

명확히 기록한다:

- 이는 **DB logical backup restore 측정값**이다.
- **서비스 전체 RTO가 아니다.**
- instance provisioning과 application readiness는 측정 범위 **밖**이다.
- **organizational RTO objective는 `not_established`**이며, artifact의
  `objective_seconds`는 `null`을 유지한다. 측정값이 목표값을 자동 생성하지 않는다.

## 8. RPO evidence 상세

관측 시퀀스:

1. backup 전 probe row A(`probe-before-backup`) 삽입
2. `pg_dump` 실행
3. backup 후 probe row B(`probe-after-backup`) 삽입
4. `DROP SCHEMA app CASCADE`로 schema 제거
5. `pg_restore` 실행
6. A는 복원됨
7. B는 복원되지 않음 (`post_backup_write_restored: false`)

이로써 backup snapshot 시점까지 복원되고 그 이후 write는 소실된다는 recovery-point
behavior를 실제로 확인했다.

관측된 recovery point는 `backup_started_at`, `backup_completed_at`과 함께 dump 파일의
크기 및 SHA-256으로 기록된다. dump SHA-256은 해당 backup artifact를 식별하는 값이다.

명확히 기록한다:

- **organizational RPO objective는 `not_established`**이며 `objective_seconds`,
  `measured_seconds` 모두 `null`이다.
- 이 결과를 **`RPO=0`으로 해석하지 않는다.** replay나 dump가 동기적이라는 사실은
  data-loss window에 대해 아무것도 말해주지 않는다.
- **observed recovery point**(dump 시점)와 **organizational RPO objective**(허용
  데이터 손실 목표)는 서로 다른 개념이며 문서·artifact·코드에서 분리해 기록했다.
  전자는 관측됐고 후자는 미수립이다. 후자는 owner가 단독으로 정할 수 없는 정책 결정이다.

## 9. consistency evidence 상세

3회 전부:

- baseline fingerprint: `d35a066a5cd1816bd4bd3fdd42c2952a2f9b0e98b3474ba7c0f8fe56463212c3`
- restored fingerprint: `d35a066a5cd1816bd4bd3fdd42c2952a2f9b0e98b3474ba7c0f8fe56463212c3`
- `consistent = true`
- probe row count pre/post 일치, probe digest pre/post 일치
- `post_backup_write_restored = false`

교차 확인: 이 fingerprint는 `migration_replay` backend가 산출한 값과 동일하다. 서로
독립적인 두 복구 경로가 같은 카탈로그로 수렴한다.

## 10. disposable DB safety

- 운영 DB 사용하지 않았다.
- 공용 DB 사용하지 않았다.
- `DE/compose.yaml`의 persistent DB 사용하지 않았다.
- run마다 **새 disposable 컨테이너를 생성**해 완전 격리했다(이전 run의 상태를 물려받지 않음).
- 모든 destructive operation(migration 적용, `pg_dump`, `DROP SCHEMA`, `pg_restore`)
  **직전에** disposable target을 재검증한다. 서버에 `current_database()`,
  `current_user`, `application_name`을 직접 질의해 계약과 대조하고, DB명에 disposable
  마커가 포함되는지 확인한다. DSN 파싱은 무엇을 요청했는지를 증명할 뿐이므로 서버가
  실제로 무엇인지를 별도로 확인한다.
- target mismatch 시 `DisposableTargetError`로 **fail-closed** 하며 쓰기 이전에 중단한다.
- **fallback DB가 없다.** 기존 컨테이너나 이미 존재하는 다른 DB로 대체 실행하지 않는다.
- run 종료 후 disposable 컨테이너를 폐기했고, dump 파일은 `finally`에서 삭제된다.
  dump 디렉터리가 비어 있음을 확인했다.
- dump 파일은 저장소 밖에 생성되며 commit 대상이 아니다.

## 11. scope limitation / observations

- **logical backup scope only.**
- WAL archiving 없음.
- PITR(point-in-time recovery) 없음.
- `pg_basebackup` 없음.
- physical replication 없음.
- HA / failover 없음.
- backup scheduler / retention policy / encryption policy 없음.
- **production DR capability라고 주장하지 않는다.** 이 구현은 요청 시 dump를 만들고
  복원하는 drill이다.
- organizational RTO objective **not established**.
- organizational RPO objective **not established**.
- local integration run은 **approved CI/staging execution과 동등하지 않다.**
  external signer / SBOM / trusted-root 입력을 로컬 placeholder로 채웠으며, gate는
  해당 입력의 존재 여부만 검사한다.
- `pg_dump` / `pg_restore` client `18.4` ↔ PG17 server 조합이며, 호환성은 별도
  spike로 사전 실증했다. CI에서는 동일 major 정렬이 더 안전하다.
- probe 데이터는 fixture 수준(1~2행)이다. 대용량 복원 성능은 측정하지 않았다.
- 측정은 로컬 단일 환경 표본이며 하드웨어 의존적이다.

## 12. public safety

이 문서와 commit된 3개 파일에 다음을 포함하지 않았다: 개인 실명, 이메일, 개인 GitHub
username, 로컬 절대경로, old/private repository 식별자, SSH/internal IP, actual DSN,
password/credential, token/API key, dump 절대경로.

구현 측 통제:

- artifact는 DSN·host·port·database name·credential을 기록하지 않는다.
- backup 파일은 **basename만** 기록한다(절대경로 없음).
- 외부 driver/DB 오류는 접속 정보를 인용하므로 `error_type`과 withheld detail만
  기록하고, 저장소가 직접 작성한 contract 오류만 메시지를 남긴다.
- password는 커맨드라인에 올리지 않고 환경변수로만 전달한다.
- 위 통제는 테스트로 강제되며, 성공·실패·차단 경로 모두를 대상으로 검사한다.
- commit metadata의 author/committer email은 GitHub noreply 주소다.

## 13. QuantQA:v1 참고 상태

`QA-WBS-01`(`docs/qa/quantqa-v1-contract.md`)은 Status `DRAFT FOR REVIEW`,
Approval `PENDING`이다. 따라서 아래는 **참고 기록이며 Done·QA의 추가 필수조건으로
사용하지 않는다.** 이 행의 판정 기준은 WBS 원문의 Done·QA 계약이다.

- S = `PASS`
- R = `PASS`
- O = `PARTIAL`
- C = `N/A`

## 14. 결과

WBS Done·QA 계약은 `RTO/RPO/consistency evidence`를 요구하며, RTO/RPO objective의
수립을 요구하지 않는다. objective 미수립은 위 11절의 observation으로 기록하며 Done
조건으로 추가하지 않는다.

- `Owner execution result: PASS`
- `Done·QA contract: satisfied`
- `Independent QA verdict: pending`
- `self-QA: no`

이 행이 WBS 상 `완료`로 전이하려면 증적 묶음 URI와 함께 approver의 검토자·검토일
기록이 필요하다. 그 판정은 WBS-designated approver가 수행한다.
