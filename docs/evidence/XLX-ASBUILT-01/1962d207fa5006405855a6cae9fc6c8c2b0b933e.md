## Canonical reconciliation 방법

WBS export snapshot의 132개 행 전체를 대상으로, 각 행의 증적 텍스트에서 커밋 SHA·PR·Issue 참조를 추출한 뒤 canonical repo에서 다음을 직접 확인했다: 객체 존재 여부, `origin/main` 조상 여부, 원격 브랜치 소속 여부, dangling(로컬 전용) 여부, `docs/evidence/<ID>/` 존재 여부와 그 안의 verdict-라벨 기반 독립 reviewer APPROVE 존재 여부. 인용된 SHA가 main의 조상이 아닌 경우, 그 SHA가 속한 브랜치 또는 행 텍스트가 직접 인용한 PR 번호를 추적해 해당 PR의 실제 merge 결과 커밋까지 확인했다(squash-merge로 SHA가 바뀌는 경우를 잡기 위함). WBS 셀의 `상태`(완료/증적대기) 텍스트는 그 자체로 신뢰하지 않고, 이 canonical 근거로만 최종 분류했다.

**용어 구분**: 이 문서에서 "canonical artifact/tested SHA"는 다음 여러 종류를 포괄하는 표현이다 — 전부를 "implementation commit"이라고 부르지 않는다.
- **implementation SHA**: 기능을 실제로 구현한 커밋(예: `P1-OBS-01`의 근거 커밋)
- **merge-result SHA**: PR이 squash-merge되며 만들어진 최종 커밋(예: `CORE-REB-01`의 `4bc3148`, `P1-JOB-01`의 `f13ab46` — 개발자가 인용한 원 커밋과 SHA가 다름)
- **tested SHA / baseline SHA**: QA가 실제로 실행된 code baseline. 현재 이 프로젝트의 evidence 파일명은 주로 이 SHA를 사용한다(예: `QA-DATA-AUDIT-02`/`04`의 `95aafc7`처럼 특정 기능 구현을 가리키지 않는 경우도 있고, `PM-GOAL-00`/`01`/`P1-OBS-01`처럼 origin/main 기준선을 가리키는 경우도 있다).
- **evidence commit**: 해당 Markdown evidence 파일 자체를 저장소에 추가·수정한 Git commit. tested SHA(및 그것을 담은 파일명)와는 별도로 관리되며, 서로 다른 값일 수 있다.

## Consistency audit — 최초 automated reconciliation의 오류와 수정 내역

**이 절은 숨기지 않는다.** 최초 automated reconciliation에는 실제 오류가 있었고, 제출 전 별도 consistency audit을 거쳐 수정했다.

### 1. `CORE-REB-01`
- 인용된 SHA `33866da...`(pre-squash) 자체는 `origin/main`의 조상이 **아니다**(이 사실 판정 자체는 맞았음).
- 그러나 이 커밋이 속한 PR이 실제로 병합됐고, 그 merge-result SHA `4bc3148...`은 `origin/main`의 조상이다.
- 최초 automated pass는 PR 병합 결과까지 추적하지 않아 "아직 병합되지 않음"처럼 오분류했다.
- **최종 분류: `EVIDENCE_PENDING`** (canonical artifact는 확인되나 독립 reviewer APPROVE evidence 없음)

### 2. `P1-JOB-01`
- 인용된 SHA `02a05416...`은 소스 브랜치가 삭제되어 현재 어떤 원격 브랜치에도 속하지 않는 dangling 상태다(이 사실 판정 자체는 맞았음).
- 그러나 같은 행 텍스트가 직접 인용한 PR 번호를 추적한 결과, 그 PR의 merge-result SHA `f13ab461...`은 `origin/main`의 조상이다.
- 최초 automated pass는 인용된 특정 SHA만 검사하고 같은 행의 PR 인용을 별도로 추적하지 않아 완전 미반영(`LOCAL_ONLY`)으로 오분류했다.
- **최종 분류: `EVIDENCE_PENDING`**

### 3. `P0-BE-02`
- evidence 문서에 "최종 승인(APPROVE) 여부: … 승인자의 최종 승인 여부는 이 evidence와 별개로 결정한다"라는, **승인 보류를 설명하는 문장 속의 "APPROVE"** 단어가 있었다.
- 최초 automated pass는 문맥 없이 이 단어를 승인으로 오탐했다.
- 실제 evidence 내용은 `QA verdict: PASS`(로컬 QA 기준)이며 최종 승인은 별도 절차로 보류돼 있다.
- **수정된 reviewer decision: `PASS / final approval pending`**
- **분류: `IMPLEMENTED_NOT_APPROVED`** (수정 전후 분류 결과는 동일했으나, 표시된 reviewer decision이 분류와 모순되는 문제를 정정했다)

### 4. `QA-DATA-AUDIT-02`, `QA-DATA-AUDIT-04`
- 두 행이 공유하는 SHA `95aafc7...`는 이 두 행의 implementation SHA가 **아니다**.
- evidence 문서 자체에 "tested_sha(fetch 시점의 `Quant_agent/main` HEAD)"로 명시돼 있다 — QA 실행 시점의 baseline일 뿐, 우연히 무관한 다른 작업(PR #15)의 merge commit과 SHA가 같다.
- 두 행은 새 구현 커밋이 없는 **QA-gate형 감사 행**이며, 기존 테스트 파일을 baseline SHA에서 재실행한 결과를 기록한 것이다.
- 두 evidence 문서 모두 `QA verdict: APPROVE`가 명시적으로 라벨링돼 있고 baseline SHA가 main의 조상임을 확인했으므로 분류 자체(`VERIFIED_APPROVED`)는 그대로 유지하되, "canonical commit" 표기를 "implementation SHA"가 아니라 "tested SHA(baseline)"로 정정했다.
